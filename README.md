# Go 后端 + AI / Agent 52 周自学系统

唯一使用入口：[学习系统.html](./学习系统.html)

## 这套系统的作用

这不是一份需要从头通读的教材，也不是把网上文章堆在一起的收藏夹。它的作用是把分散的 Go 后端、数据库、中间件、分布式、系统设计、算法、RAG 和 Agent 资料，整理成一条每周都能执行、能验收、能留下项目证据的 52 周路线。

它主要解决五个问题：

1. **不知道先学什么。** 全年按前置关系排列，先补 Go 工程基本盘，再进入数据库、中间件、网络、分布式和生产项目，最后学习 RAG、Agent、MCP、安全与评测。
2. **资料很多但不知道看哪里。** 每周默认只有一份中文主资料，并明确“只看哪些章节、看到哪里停止”。官方文档和其他链接只用于核对，不要求全部阅读。
3. **看懂了却不会做。** 每周必须留下代码、测试、故障实验、设计图、评测结果或口述记录，不能只用阅读时长代表掌握。
4. **学过但面试讲不出来。** 每周都有无辅助问题和通过门槛；关掉资料和 AI 后仍能解释，才算掌握。
5. **在职学习容易把计划排满。** 计划按每周而不是每天安排，给加班、卡点和补课保留时间，不要求把 16–18 小时全部塞满。

## 适合谁

当前版本专门按以下情况设计：

- 已经从事 Go 后端开发约一年；
- 不是编程入门者，但缺少系统学习；
- 半年内没有强制跳槽期限，希望用一年稳步补齐体系；
- 工作日每天约 2 小时，周末合计约 6–8 小时；
- 求职方向仍以 Go 后端为主，同时希望具备 AI 应用、RAG 和 Agent 工程能力。

它不适合作为 Go 零基础速成课，也不是两三个月突击面试题的安排。

## 一年结束后希望获得什么

最终目标不是“看完 52 周网页”，而是得到以下可验证结果：

- 能解释 Go 的错误、接口、`context`、并发、调度、GC、逃逸、测试和性能排查；
- 能分析 MySQL、Redis、Kafka、事务、缓存一致性、幂等、Outbox 和故障恢复；
- 能沿 DNS、TCP/TLS、HTTP/RPC、Linux、微服务和可观测性排查一次线上请求；
- 能用统一流程完成系统设计，说明容量、正确性、可用性、失败边界和演进取舍；
- 完成两个后端项目：ShortLink 和 ReliableTask；
- 完成两个 AI 工程项目：DeepRAG 和只读 OnCall Agent；
- 全年完成 90 道核心算法新题及间隔复做，而不是临近面试突击刷题；
- 留下一套能用于简历、项目答辩和面试表达的代码、测试、图表、评测与复盘证据。

## 全年七个阶段

| 阶段 | 周次 | 主要作用 | 阶段结果 |
| --- | --- | --- | --- |
| Go 工程根基 | W1–W8 | 把“会写 Go”升级为能测试、评审和排障 | 建立可取消、可测试、可诊断的 Go 工程基线 |
| 数据与中间件 | W9–W16 | 学会在并发、故障和数据增长下保证正确性 | 完成 ShortLink，留下索引、事务、缓存和消息故障证据 |
| 服务端与分布式 | W17–W24 | 把网络、OS、RPC、微服务、稳定性和观测串成请求链 | 为六类系统设计题写出骨架，完整讲透其中一题 |
| 生产级 Go 项目 | W25–W32 | 把前 24 周能力压进一个可恢复的工程项目 | 完成 ReliableTask 的状态机、幂等、重试、背压和观测闭环 |
| LLM 与 DeepRAG | W33–W40 | 从模型调用进入检索、排序、评测和降级 | 完成有固定评测集和前后对比数据的 DeepRAG |
| Agent、MCP 与效果工程 | W41–W48 | 让工具调用、权限、状态、失败和成本可控 | 完成只读 OnCall Agent 及安全、轨迹和回归评测 |
| 年度整合与职业证据 | W49–W52 | 区分“看过”和“能够独立使用” | 完成后端与 Agent 综合验收、项目复盘和下一季度计划 |

Go 后端始终是主线。AI 部分建立在 Go 工程、数据库、分布式、稳定性和可观测性之上，不会为了追逐框架而跳过后端基本盘。

## 每周应该怎样使用页面

页面视觉上按照编号展示信息，但实际执行建议按下面顺序进行。

平时只需要停留在当前周工作台。需要找其他周时，点击顶部“全年地图”，在全屏地图顶部直接选择 W01–W52，再点“进入所选周”；也可以先选七个阶段，再点阶段中的周卡片。选周后地图会自动关闭，按 `Esc` 也能随时收起。地址栏会保留 `#W24` 这样的周次定位，可以收藏或直接发给自己。

### 第一步：先看“01 本周的前后关系”

这里回答四个问题：这周从上一周接过什么、只解决什么、完成后留下什么，以及为下一周准备什么。它的作用是防止把 52 周看成 52 个互不相关的知识点。

### 第二步：看“03 本周学习路线”

`L1、L2、L3` 表示本周真正需要掌握的学习点。先把这些学习点看明白，再开始任务。页面写了“学到能用于哪个任务、能回答哪个问题就停止”，不要求继续向外扩展。

### 第三步：看“04 本周只跟一份主资料”

`M1` 是本周默认主资料。只阅读卡片中“只看”的范围：

- 主资料已经足够，就不要切换网站；
- 遇到主资料没有覆盖的 API、机制或边界，再打开右侧备用核对链接；
- 不需要确认长文档里的每一项内容；
- 不把“收藏了很多链接”当成学习成果。

资料筛选优先级是：中文高质量讲解负责理解，官方文档或一手资料负责核对关键机制。社区资料不被当作不可质疑的标准，官方资料也不要求整站通读。

### 第四步：完成“02 本周实战交付”

`T1、T2、T3、T4` 是本周真正需要做的任务。每项任务都包含具体含义、实际例子、执行步骤和最终交付物。

任务的作用是把知识变成可检查的工程能力。证据可以是代码、自动测试、设计图、压测原始数据、故障记录、评测集、录音或复盘文档。

### 第五步：完成“05 无辅助验收”

`Q1、Q2、Q3` 必须在关掉资料和 AI 后回答。勾选问题只代表完成检查，不代表已经通过；还需要满足页面给出的 Gate。

无辅助验收用来区分“看到答案时觉得自己懂了”和“真正能够独立解释、实现、分析和做取舍”。没有通过时，只修复最低分或最关键的缺口，不重新通读整份资料，也不同时增加更多课程。

### 近两年社招迁移题的作用

每周的无辅助验收中增加了一道“近两年社招迁移题”，但它**不是另一套面试题课程**：

- 题目只从已经核对的 2025–2026 大厂社招样本中抽取信号，再改写成与本周知识对应的场景；
- 每周只做一道，约 10–15 分钟，已经包含在“无辅助验收约 60 分钟”内，不增加周负荷；
- 它负责检查能否把本周知识迁移到项目追问、故障场景或现场编码，不单独阻塞 Gate；
- 每题旁边只显示“回答至少覆盖”的三项要点，需要时再展开面经依据，不要求逐篇阅读；
- 全年地图把这些信号汇总为七条主线：项目深挖、Go 工程、数据与中间件、服务与稳定性、生产项目、LLM/Agent、算法。

面经是个人回忆，只能证明“近期有人问过”，不能证明题目固定、答案正确或所有部门都会问。因此课程知识仍由中文高质量讲解建立理解，由官方文档核对机制；面经只用于校验覆盖和训练表达。

### 第六步：记录本周证据和复盘

填写实际用时、产物位置、主要阻塞和下周策略。进度保存在当前浏览器的本地存储中；清除浏览器站点数据或更换浏览器后，勾选记录可能不会保留，因此重要证据仍应放在自己的代码仓库或文档目录中。

## 时间安排为什么这样设计

你的每周可用时间约为 16–18 小时，但计划不会全部占满：

- 普通学习周：核心任务 10–12 小时；无辅助验收约 1 小时；算法 1.5–2 小时；合计约 12.5–15 小时。
- 阶段验收周：不新增大块知识，核心任务通常 7–10 小时，验收已经包含在核心时长里；加算法后通常约 8.5–12 小时。
- W52：只做年度复盘和下一阶段计划，约 7.5–10 小时。

全年核算后的平均负荷约为 13.2 小时/周，低于可用的 16–18 小时。留下的时间用于加班、家庭事务、实验卡住、补弱和休息，而不是继续加资料。

如果某周工作特别忙：

- 普通周优先完成 T1，其他任务顺延；
- 不用为了保持日历进度而草率勾选通过；
- 阶段验收周优先补齐前面阶段最薄弱的一项；
- 允许整条路线向后顺延，不需要删掉后面的关键主题。

## 阶段验收周有什么作用

W8、W16、W24、W32、W40、W48、W52 是低负荷验收与补课节点。它们不是再上一周新课，而是检查前一个阶段的知识能否被独立使用。

以 W24 为例：

1. 六类系统设计题各做一张 20 分钟骨架，不是完成六套完整架构；
2. 随机抽其中一题，进行一次 60 分钟完整设计；
3. 只围绕同一道题接受容量、一致性、热点、降级和观测追问；
4. 只修最低分项，再回答一个变式。

W24 的主资料只看五处：如何处理一个系统设计的面试题、预估计算量、缓存、异步、设计 Pastebin.com（或者 Bit.ly）。最多阅读 60 分钟，不通读整个仓库，也不逐条验证全文。

## 算法副线的作用

算法不是独立的突击训练营，而是全年保持编码和复杂度分析手感的副线：

- 每周约 1.5–2 小时；
- 普通周学习少量新题，并按间隔复做旧题；
- 七个阶段验收周不增加新题；
- 覆盖数组、哈希、字符串、链表、栈、队列、堆、树、图、BFS/DFS、回溯、贪心和基础 DP；
- 验收重点是能独立写出、解释复杂度、处理边界，而不是累计提交数量。

## 四个项目分别证明什么

| 项目 | 作用 | 关键证据 |
| --- | --- | --- |
| ShortLink | 证明能够处理索引、事务、缓存一致性和消息重复 | API、EXPLAIN、并发测试、缓存故障测试、答辩稿 |
| ReliableTask | 证明能够设计可恢复的生产级异步任务系统 | 状态机、幂等、租约、重试、Outbox、背压、故障注入、观测 |
| DeepRAG | 证明 RAG 优化不是凭感觉，而是有固定评测和前后数据 | 评测集、HitRate/MRR、忠实度、失败归因、before/after |
| OnCall Agent | 证明 Agent 能在受限权限内安全、可追踪地调用真实工具 | MCP Server、只读工具、轨迹日志、攻击评测、成本与失败报告 |

## 明确不作为当前重点的内容

为了保证一年内可执行，以下内容只要求知道边界，暂不展开为专项：

- Go runtime 或 Linux 内核源码级细节；
- Raft 代码实验和形式化一致性证明；
- 同时学习多个消息队列或多个 Agent 框架；
- 把 Self-RAG、CRAG、GraphRAG 全部实现一遍；
- 模型预训练、RLHF、LoRA 实操和 GPU 推理优化；
- 复杂 Multi-Agent 平台、多租户控制面和跨云部署。

这些主题并非没有价值，而是它们对当前“Go 后端主线 + Agent 工程拓展”的投入产出较低，容易挤占项目与面试基本盘。

## 资料与正确性原则

这套路线参考了小林 Coding 对外公开的训练营模块和服务流程，但没有复制、购买、破解或传播其私有课程资料。这里提供的是公开资料替代路线。

资料采用以下规则：

1. 优先使用仍可访问、长期维护、社区使用广泛的中文资料；
2. 关键 API、协议和行为边界使用官方文档或一手规范核对；
3. 英文官方文档默认放在备用核对区，不作为每周主要讲解材料；
4. 每周只指定精确阅读范围，不要求整站通读；
5. 旧项目、停止维护的仓库或只适合历史参考的资料会降级标注；
6. 任何博客都可能过时，涉及生产配置、安全和版本差异时，以当前官方文档和所在公司的实际环境为准。
